паттерны и эксплуатация в production.

# Часть I. Основы

# Глава 1. Что такое BPM

Business Process Management (BPM) --- подход к проектированию,
автоматизации и сопровождению бизнес-процессов.

Бизнес-процесс представляет собой последовательность действий, которые
выполняются для достижения конкретного результата: оформления заказа,
выдачи кредита, регистрации пользователя, обработки страхового случая и
т.д.

Главная задача BPM --- отделить бизнес-логику процесса от прикладного
кода.

Вместо длинной цепочки вызовов внутри Java-приложения процесс
описывается декларативно в виде BPMN-схемы. Process Engine отвечает за
выполнение этой схемы, сохранение состояния, управление транзакциями и
восстановление после ошибок.

Именно это отличает Camunda от обычного набора сервисов.

В следующих главах будут подробно рассмотрены история платформы,
архитектура движка и принципы его работы.

# Глава 2. История Camunda

## 2.1. Почему появились BPM-движки

Первые корпоративные BPM-системы создавались как инструменты для
автоматизации сложных бизнес-процессов крупных компаний. IBM, Oracle,
SAP и другие поставщики предлагали мощные платформы, однако они были
дорогими, сложными во внедрении и сильно зависели от конкретного
вендора.

Большинство подобных решений строилось вокруг идеи Low-Code или No-Code.
На практике это приводило к тому, что бизнес-аналитики не могли
самостоятельно реализовать процессы, а разработчики были вынуждены
использовать закрытые инструменты и нестандартные технологии.

Именно в этот момент появилась потребность в открытом BPM-движке,
ориентированном на разработчиков.

------------------------------------------------------------------------

## 2.2. jBPM

В 2003 году Том Байенс создал jBPM --- один из первых популярных
BPM-движков с открытым исходным кодом.

Основные преимущества:

-   Java как основной язык разработки;
-   возможность встраивания движка в приложение;
-   поддержка выполнения процессов;
-   открытый исходный код.

Главным недостатком стал собственный язык описания процессов (jPDL),
несовместимый с другими продуктами.

------------------------------------------------------------------------

## 2.3. Activiti

В 2010 году появился Activiti.

Ключевым изменением стала поддержка международного стандарта BPMN 2.0.

Это позволило:

-   переносить схемы между инструментами;
-   использовать единый стандарт моделирования;
-   отделить описание процесса от конкретной реализации движка.

Именно Activiti стал основой для дальнейшего развития Camunda.

------------------------------------------------------------------------

## 2.4. Появление Camunda

В 2013 году команда Camunda отделилась от Activiti и создала собственный
форк.

Основные причины:

-   развитие Enterprise-функций;
-   повышение стабильности;
-   улучшение производительности;
-   создание профессиональных инструментов эксплуатации (Cockpit,
    Tasklist, Optimize).

Camunda быстро стала одним из самых популярных BPM-движков в
Java-экосистеме.

------------------------------------------------------------------------

# Глава 3. Camunda 7 и Camunda 8

Несмотря на общее название, Camunda 7 и Camunda 8 имеют принципиально
разную архитектуру.

Camunda 7             Camunda 8
  --------------------- ----------------------
Java Process Engine   Zeebe
Реляционная БД        Event Log + RocksDB
Java Delegate         Job Worker
REST + Java API       gRPC
ACID-транзакции       Eventual Consistency
Embedded Engine       Cloud Native

## Когда выбирать Camunda 7

Camunda 7 подходит если:

-   приложение написано на Spring Boot;
-   требуется общая транзакция с БД;
-   большая часть логики реализуется на Java;
-   необходимы Java Delegate.

## Когда выбирать Camunda 8

Camunda 8 предпочтительна если:

-   используется Kubernetes;
-   система состоит из множества микросервисов;
-   необходима высокая горизонтальная масштабируемость;
-   большинство операций выполняется асинхронно.

# Глава 4. Архитектура Camunda 7

Camunda 7 представляет собой встроенный Process Engine.

Основные компоненты:

    Client
        │
    REST / Java API
        │
    Process Engine
        │
    PVM
        │
    Command Executor
        │
    Persistence Layer
        │
    PostgreSQL

Во время запуска процесса движок выполняет несколько последовательных
этапов:

1.  Загружает BPMN-модель.
2.  Создает экземпляр процесса.
3.  Формирует Execution.
4.  Выполняет очередной BPMN-элемент.
5.  Сохраняет состояние.
6.  Переходит к следующему элементу.

------------------------------------------------------------------------

## Глава 5. Process Virtual Machine (PVM)

### Что такое PVM

Process Virtual Machine (PVM) - внутренний исполнитель Camunda 7.
BPMN-диаграмма сама по себе не выполняется: после развертывания движок
преобразует её в граф объектов PVM, а затем исполняет его с помощью
набора атомарных операций.

Именно PVM отвечает за переход между элементами процесса, создание
параллельных ветвей, завершение задач и обработку событий.

### Основные сущности

**Activity** --- узел процесса.

**Transition** --- переход между двумя узлами.

**Scope** --- область видимости процесса или подпроцесса.

**Execution** --- объект, представляющий текущее состояние выполнения
процесса.

### Atomic Operations

Любое действие разбивается на последовательность небольших операций.

Типичный цикл выполнения выглядит следующим образом:

1.  Вход в элемент.
2.  Выполнение поведения элемента.
3.  Обновление состояния Execution.
4.  Поиск следующего перехода.
5.  Передача управления следующему элементу.

Такой подход позволяет выполнять процессы независимо от типа
BPMN-элемента.

# Глава 6. Execution

Execution --- центральная сущность Camunda Runtime.

Каждый активный процесс имеет как минимум один объект Execution.

При появлении параллельных ветвей создаются дополнительные Execution,
формирующие дерево выполнения.

Пример:

``` text
Process Instance
        │
 Root Execution
      /   \
Execution Execution
```

Execution хранит:

-   текущий BPMN-элемент;
-   ссылку на определение процесса;
-   родительский Execution;
-   состояние выполнения;
-   ссылки на переменные процесса.

Важно различать Process Instance и Execution. Один экземпляр процесса
может содержать множество объектов Execution.

# Глава 7. Persistence Layer

Одной из ключевых особенностей Camunda является сохранение состояния
процесса после каждой транзакционной границы.

Для этого используется реляционная база данных и набор системных таблиц.

### Основные группы таблиц

**ACT_RE\_\*** --- определения процессов.

-   ACT_RE_PROCDEF
-   ACT_RE_DEPLOYMENT

**ACT_RU\_\*** --- текущее состояние процесса.

-   ACT_RU_EXECUTION
-   ACT_RU_TASK
-   ACT_RU_VARIABLE
-   ACT_RU_JOB

**ACT_HI\_\*** --- история выполнения.

-   ACT_HI_PROCINST
-   ACT_HI_ACTINST
-   ACT_HI_VARINST
-   ACT_HI_TASKINST

**ACT_GE\_\*** --- общие данные движка.

**ACT_ID\_\*** --- пользователи, группы и арендаторы.

### Почему Runtime и History разделены

Runtime содержит только активные процессы.

После завершения процесса большинство Runtime-записей удаляется, а
необходимые данные переносятся в History.

Это позволяет поддерживать высокую производительность даже при большом
количестве завершённых процессов.

# Глава 8. Транзакционная модель

Camunda использует транзакционную модель, основанную на точках
сохранения состояния (Wait States).

К ним относятся:

-   User Task;
-   Receive Task;
-   Message Catch Event;
-   Signal Catch Event;
-   Timer Event;
-   элементы с asyncBefore;
-   элементы с asyncAfter.

До достижения очередной точки ожидания процесс считается одной
транзакцией.

Если возникает ошибка, выполняется откат к последнему сохранённому
состоянию.

Именно поэтому долгие операции рекомендуется отделять с помощью
asyncBefore или asyncAfter.

# Глава 9. Command Pattern

Практически любое действие в Camunda реализовано как Command.

Типичный жизненный цикл команды:

``` text
Java API / REST
        │
Command Executor
        │
Interceptors
        │
Command Context
        │
PVM
        │
Persistence
```

CommandContext открывает транзакцию, управляет кэшем сущностей и
выполняет синхронизацию изменений с базой данных.

Такой подход делает выполнение процессов атомарным и гарантирует
согласованность состояния.

# Глава 10. Job Executor

Job Executor отвечает за выполнение асинхронных задач.

Архитектура состоит из трёх компонентов:

1.  Job Acquisition --- поиск доступных задач.
2.  Thread Pool --- выполнение задач.
3.  Locking --- защита от конкурентного выполнения.

Основные параметры настройки:

``` yaml
camunda.bpm.job-execution:
  enabled: true
  core-pool-size: 10
  max-pool-size: 50
  max-jobs-per-acquisition: 10
  lock-time-in-millis: 300000
```

При высокой нагрузке рекомендуется:

-   включить Deployment Aware;
-   увеличить размер пула потоков;
-   подобрать lockTime под длительность задач;
-   использовать asyncBefore после Parallel Gateway для уменьшения
    количества Optimistic Locking Exception.

Следующая часть книги будет посвящена BPMN и рассмотрит все элементы
стандарта без повторов и пересечений.
